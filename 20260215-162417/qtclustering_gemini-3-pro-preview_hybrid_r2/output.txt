Wait, re-computing on CPU is cheap ($O(N^2)$) compared to the $O(N^3)$ search. The search is checking $N$ seeds. Re-constructing the winner is just checking 1 seed.
So the GPU kernel only needs to return the **cardinality** for each seed.
This simplifies things a lot. We don't need to store the clusters.

**Algorithm for GPU Kernel:**
For each `seed_idx` in `seeds`:
1.  Initialize `current_cluster` with `seed`.
2.  Loop:
    *   Find `best_candidate` among all points that are not in `global_clustered` and not in `current_cluster`.
    *   Condition: `max(dist(candidate, member)) < threshold` for all `member` in `current_cluster`.
    *   Metric: minimize `max(dist(candidate, member))`.
    *   If no candidate fits, break.
    *   Add `best_candidate` to `current_cluster`.
    *   Increment `size`.
3.  Store `size`.

**Optimization:**
*   The distance matrix is constant. We can precompute it? $N=1000 \implies 1000^2 \times 4$ bytes $\approx 4$ MB. Fits in cache/shared/texture.
*   If $N$ is larger, we compute on the fly.
*   The `current_cluster` grows. Checking `max_dist` involves iterating over the cluster.
*   This looks like a lot of work for one thread.
*   Maybe use a block per seed?
    *   If we use a block per seed, we can parallelize the "find best candidate" step.
    *   To find the next point:
        *   Each thread checks a subset of candidate points.
        *   For a candidate point, it checks distance to all current cluster members.
        *   Reduce to find the best candidate for this step.
        *   Add to cluster.
